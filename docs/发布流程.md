# SubNest 发布流程

本文是维护者每次发布新版本时必须执行的固定流程。正式版本只使用一份中文发布说明，不额外创建英文发布说明，也不在 README 增加版本说明跳转。

## 以前反复失败的原因

1. 版本标签先推送，中文发布说明尚未提交，流水线找不到 `docs/release-notes/v版本号-zh.md`。
2. 稳定版标签建立在功能分支，提交不属于 `main` 历史，正式发布被拒绝。
3. 新增界面文案后只修改描述文件，没有运行翻译目录生成，Cloudflare 检查失败。
4. Docker 镜像与 Cloudflare 检查并行执行，Cloudflare 失败时镜像已经推送，形成半发布状态。
5. 本机使用 Node 20 执行 Lingui/Vite，而项目要求 Node 24.19 以上，导致本地验证结果不完整。
6. GitHub Release 没有创建时，页面虽然能发现新版本号，但缺少 Linux 更新包，页面内更新不可用。

## 固定发布顺序

1. 完成代码修改和测试，不创建版本标签。
2. 使用 Node 24.19 或更高版本安装依赖。
3. 新增或修改界面文案后运行 `pnpm --filter @renewlet/client i18n:extract`。
4. 创建唯一的中文发布说明：`docs/release-notes/v版本号-zh.md`。
5. 运行 `node scripts/release.mjs sync-version 版本号`，同步所有 package 版本与 Docker 示例。
6. 运行 `node scripts/release.mjs preflight 版本号`。任何错误都必须修复，不能跳过。
7. 运行后端测试、前端类型检查和必要的页面测试。
8. 提交所有代码、生成目录、版本号和中文发布说明。
9. 先将提交合并或快进到 `main`，确认远端 `main` 包含本次提交。
10. 最后创建并推送 `v版本号` 标签。
11. 等待 Release Publish 全部完成，不能只看 Docker 成功。
12. 检查 GitHub Release 已创建，并确认包含以下附件：
    - `renewlet-docker-v版本号.zip`
    - `renewlet_版本号_linux_amd64.tar.gz`
    - `renewlet_版本号_linux_arm64.tar.gz`
    - `checksums.txt`
13. 在系统更新页面重新检查，确认页面内更新按钮可用后，本次发布才算完成。

## 自动保护措施

- `preflight` 会拒绝 Node 24.19 以下的环境。
- `preflight` 会检查所有 workspace 版本号、README Docker 固定版本、中文发布说明、翻译目录、部署配置和 Docker 部署附件。
- 稳定版标签必须来自 `main` 历史。
- E2E 和 Cloudflare 构建检查通过后，才允许推送正式 Docker 镜像。
- Docker 与 Cloudflare 成功后，才会创建 GitHub Release 和 Linux 页面内更新附件。
- 任一任务失败时，不得手工宣告发布完成；修复提交进入 `main` 后，重新建立同版本标签并完整重跑。
